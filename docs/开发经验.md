# 开发经验与踩坑记录

记录本项目开发中遇到的实际问题、根因与教训，供后续迭代参考。

## 1. Edge Function 写库字段必须与迁移 SQL 严格对齐

**案例**：`generate-daily-copy` 成功生成文案后写入 `daily_cards` 表时，函数里写了 `provider` 字段，但建表 SQL 漏了该列，报 `PGRST204: Could not find the 'provider' column of 'daily_cards' in the schema cache`。AI 链路其实已成功（aixluv 502 后切 SU8 兜底成功），是最后写库一步因缺列失败。

**教训**：部署/发布 Edge Function 前，必须把函数内所有 `from(表).insert/update` 涉及的字段与迁移 SQL **逐列核对**。schema 变更后要先执行迁移、再部署函数，顺序不可颠倒。

**检查清单**（改表或加函数时逐项过）：
- 列名与类型：函数写入的每个字段在表中都存在且类型兼容
- 主键/唯一约束：upsert 的 `onConflict` 列是真实存在的约束
- RLS 策略：`FOR ALL TO authenticated` + `auth.uid() = user_id` + 非匿名校验
- GRANT：`GRANT SELECT, INSERT, UPDATE, DELETE ... TO authenticated`

## 2. 错误处理分支自身绝不能抛错（否则掩盖真实错误）

**案例**：catch 块里写了 `createClient(...).from(...).update(...).eq(...).catch(() => null)`，但 **supabase-js 的查询构建器是 thenable 不是 Promise，没有 `.catch` 方法**，于是标记失败状态时抛出 `TypeError: ...catch is not a function`，把真正的主错误（如 PGRST204）完全掩盖，用户看到的错误与根因无关，极大拖慢排查。

**教训**：
- 错误处理代码要用 `try/catch` 包裹并打日志，任何"标记失败/兜底"逻辑都不允许二次抛错
- supabase-js 查询链用 `await`，不要用 `.then/.catch`（构建器支持 await，但不支持链式 Promise 方法）
- 用户可见的错误信息应来自主流程，兜底逻辑只负责记录，不覆盖主错误

## 3. AI 上游 502 抖动是已知问题，兜底链路保证可用

**案例**：aixluv 主链路返回 `502 Upstream access forbidden`（上游抖动，周报/每日一卡都会遇到），日志显示 `provider aixluv 第 1 次失败`。

**教训**：
- aixluv 502 是上游已知抖动，代码已做 3 次重试 + 自动切换 SU8 兜底，属于正常容错，不必当作 bug
- 排查时看日志里的 `provider xxx 第 N 次失败` 与最终是否切到兜底；若所有 provider 都失败才是真问题
- 与周报共用同一套 provider 链（`buildProviders`/`pickModel`/`fetchWithTimeout`），周报可用即代表 AI 链路可用

## 4. 部署前验证边界：登录态受限时能验证什么

**案例**：`generate-daily-copy` 要求正式账号 token（非匿名）才能调用，本地无法模拟用户登录态做全链路请求测试，导致"先验证再部署"无法完全做到，用户多次反馈报错。

**教训**（受限于鉴权的函数）：
- 必须验证：构建/语法通过、AI provider 链可用（复用周报同款、或本地脚本测 provider）、**函数写库字段 ↔ 迁移 SQL 一致性**（第 1 条）
- 无法本地验证：完整请求链路（需登录 token）——应在交付时明确告知验证边界，把"执行迁移 → 用户重试确认"作为明确步骤
- 把第 1 条的字段对齐检查做成部署前必做步骤，能拦截绝大部分"生成成功但写库失败"类问题

## 5. 每日一卡 v2 架构决策（省 token 设计）

按用户"一周一次、不自动请求"的要求定稿：
- **云端批次**：`daily_cards` 表每用户一行，存一批文案（首页首批 7 条，个人配置页重新生成 14 条），生成一次用很多天
- **顺序循环**：显示 `第 (自批创建日起的天数) % 条数` 条，多设备同一天显示同一条；「换一条」只在池内切换（当天偏移存 sessionStorage，跨天归零），不消耗 token
- **绝不自动请求**：打开页面只读 `fetchDailyCards()`，生成入口只有两处（首页空态 7 条、个人配置页 14 条，后者有确认弹窗提示消耗 AI 额度）
- **首页排序**：卡片 key 数组存 `workbench_meta.home_order`（经 `syncMetaField` 白名单 `__homeOrder` 同步），首页按组分段渲染、组头自动跟随；个人配置页提供上移/下移/恢复默认/保存
- 前端模块边界：`src/lib/home-layout.js`（卡片清单，供首页渲染与设置页排序共用）、`src/lib/daily-copy.js`（批次状态与轮换）、`src/modules/settings/SettingsView.vue`（个人配置页）

## 6. 经典脚本 ↔ ES module 的回调桥接（sync-hooks.js）

`supabase-sync.js` 是经典脚本，用顶层 `let onSyncReady = null; let onRemoteUpdate = null;` 暴露两个回调钩子（分别在「全量同步完成」与「Realtime 收到远端变更」时调用）；Vue 入口 `src/main.js` 是 ES module，执行时机晚于所有经典脚本，只能把处理函数挂到 `window.__onSyncReady` / `window.__onRemoteUpdate`。`js/sync-hooks.js` 就是这两者之间的包装层。

**为什么必须转发时再读 window**：桥接脚本与入口模块的加载顺序不作为契约，包装函数内用 `const handler = root.__onSyncReady` 现取现用，两边任意先后都能生效（`tests/sync-hooks.test.js` 覆盖了两种顺序）。

**守卫写法别改错**：`typeof onSyncReady === "undefined"` 只用于判断「supabase-sync.js 完全没加载」，此时变量为 `null`，`typeof null === "object"`，守卫不生效、正常赋值。切勿改成 `if (!onSyncReady) return`——那会阻止首次赋值，钩子永远接不上。

**桥接层要吞异常**：包装函数里 `try/catch` 包住渲染层调用，否则 Vue 侧一个渲染异常会被 `supabase-sync.js` 当成「同步失败」处理。

**Vite 只重写真实存在的 public 资源**：`src/index.html` 里的 `/js/xxx.js` 只有在文件确实存在（`scripts/copy-supabase-sync.mjs` 会整目录拷贝根 `js/`）时，构建才会改写成相对路径 `./js/xxx.js`。引用一个不存在的脚本不会报错，但构建产物会保留绝对路径，导致 `tests/vue-build.test.js` 的相对路径断言失败——新增全局脚本后记得同步源码与实际文件。

## 7. 演示数据（样板数据）与账号数据隔离

问题：首次进页面 `load()` 在没有 localStorage 数据时按 `CONFIG.modules[].seed` 造样板数据存进内存；匿名会话下 `mergeDataWithCloud` 会把它写进 localStorage，注册账号时 `queueLocalAccountMigration` 又把本地记录整批迁到账号，于是样板数据变成了用户自己的数据。

- **标识在数据层打**：`load()` 里给每条样板记录加 `__seed: true`（`src/lib/demo-data.js` 的 `markSeedRecords`），只标顶层记录、不动嵌套的动作实例。用户经过 `persist()` 保存过就不再是样板，`persist` 顺手把标识删掉。
- **判定不看标识而看内容**：`isDemoRecord()` 拿记录与样板模板逐字段比对（忽略 `__seed` 与 `updated_at`，用键顺序无关的稳定序列化）。这样修复前就已经落到 localStorage / outbox 的无标识样板也能识别，而用户真正改过的记录不会被误判成演示数据。
- **三处设卡**：`syncRecord`（提前返回，连 `updated_at` 都不改）、`queueLocalAccountMigration`（跳过样板）、`processOutbox`（丢掉修复前排进 outbox 的老操作，抽成 `dropDemoOperations` 便于测试）。上云副本用 `stripSeedFlag` 去掉标识。
- **经典脚本的守卫走 `window.DemoData` 桥**（与 `window.SyncCore`、`window.CONFIG` 同一套路），桥不在时退回只看 `__seed`。
- 已污染的账号用 `purgeDemoRecords({ commit: true })` 清，默认只盘点不删，只删内容与样板完全一致的行。
- **测试用 `vm` 跑经典脚本**：`tests/seed-guard.test.js` 在一个干净上下文里加载 `sync-core.js` 与 `supabase-sync.js`，并把上下文的 `window` 指向它自己的全局对象（`sandbox.window = sandbox`）——经典脚本之间靠 `window.SyncCore = api` 互认，若把 `window` 设成一个普通对象，脚本里的裸 `SyncCore` 就解析不到。

## 8. 全局垫片（`window.X = api`）的收尾

迁 ESM 时常见做法是两头下注：文件导出 ES 模块，同时 `window.X = api` 留给还没改的调用方。收尾时必须**在同一轮里把两边都改完**：删掉定义侧的 `window.X` 赋值，同时把消费者改成 `import`。只做一半不会报错，因为消费侧普遍写成 `window.Toast?.show?.(...)` 这种可选链，删了赋值只是功能静默消失。

- 收尾前先用 `grep -rn "window\.\(Toast\|AppDialog\|…\)"` 把所有消费者列全，再逐文件改成 import；改完再 grep 一次确认零残留。
- 顺手把 `typeof RecordMedia === "undefined"` 这类“看不见就降级”的守卫删掉：直接 import 之后分支永远不会走，留着会让读者以为还有别的加载方式。
- **真正难找的是“根本没有定义方”的全局**。`daily-copy.js` 里的登录按钮读 `window.openAuthModalRef?.current?.("login")`，而 `openAuthModalRef` / `openAuthModal` 从来没有被挂到 `window` 上，可选链把“点了没反应”吞成了静默失败。判断一个 `window.X` 能不能删，不要看它写得多稳，要去全文搜它的**赋值方**；搜不到就是 bug，不是契约。
- 收尾后要用测试钉住：`tests/vue-build.test.js` 里加一条扫描 `src/**` 与 `supabase-sync.js`、禁止再出现已删垫片的用例，以后谁手滑加回来会在测试里暴露。
